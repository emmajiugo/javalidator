# Javalidator Pre-1.0.0 Improvements Design

**Date:** 2026-03-21
**Status:** Approved
**Scope:** Bug fixes, API changes, new rules, code quality, and test coverage before tagging 1.0.0

---

## 1. Bug Fixes

### 1.1 InRule Null Handling

**Problem:** `InRule.validate()` calls `String.valueOf(value)` without a null check, converting null to the string `"null"`. All other rules return null (pass) for null values.

**Fix:** Add null guard at the top of `InRule.validate()`. Return `null` for null values — let `required` handle null enforcement.

### 1.2 Numeric Comparison Precision

**Problem:** `GtRule`, `LtRule`, `GteRule`, `LteRule` use `intValue()` and `Integer.parseInt()` throughout, causing silent overflow for values > 2,147,483,647 and truncating decimals. `BetweenRule` already uses `doubleValue()` correctly.

**Fix — three changes in each rule:**
1. Parameter parsing: `Integer.parseInt(parameter)` -> `Double.parseDouble(parameter)` to support decimal thresholds like `gt:3.5`
2. Value conversion: `n.intValue()` -> `n.doubleValue()` for Number types
3. String-to-number path: `Integer.parseInt(s)` -> `Double.parseDouble(s)` for String values
4. Error message format specifiers: `%d` -> use `Number` formatting that omits `.0` for whole numbers (e.g., display "3" not "3.0" for `gt:3`)

### 1.3 Spring Metadata Defaults Mismatch

**Problem:** `additional-spring-configuration-metadata.json` says `validate-get-requests` and `validate-delete-requests` default to `false`, but `JavalidatorProperties.java` initializes them to `true`.

**Fix:** Update the metadata JSON to set both defaults to `true`. Also add missing metadata entries for `javalidator.strict-mode` (default: `false`) and `javalidator.aspect.validate-services` (default: `true`) which exist in `JavalidatorProperties` but are absent from the metadata file.

### 1.4 Spring Error Response Overwrites Duplicate Field Errors

**Problem:** When a parameter has multiple `@Rule` annotations, `ValidationAspect` correctly accumulates separate `ValidationError` objects into `allErrors`. However, `GlobalExceptionHandler` uses `errors.put(validationError.field(), validationError.messages())` — a map keyed by field name. When two `ValidationError` objects share the same field name, the second overwrites the first, losing errors.

**Example:** `@Rule(value = "required", message = "Required") @Rule(value = "min:1", message = "Too small")` on the same parameter produces two `ValidationError("userId", ...)` objects. The map keeps only the last one.

**Fix:** In `GlobalExceptionHandler`, merge messages for the same field instead of overwriting. Check if the field key already exists and concatenate the message lists.

## 2. API Changes

### 2.1 ValidationError Enrichment

**Problem:** `ValidationError(String field, List<String> messages)` provides no programmatic way to identify which rules failed. This blocks i18n, conditional UI logic, and error handling.

**Change:** Extend the record to:

```java
record ValidationError(String field, List<String> messages, List<String> rules)
```

- `rules` is always populated with failed rule names (e.g., `["required", "min"]`)
- `messages` remains human-readable (custom or default)
- Lists are parallel: `rules.get(i)` corresponds to `messages.get(i)`

**Internal wiring — how rule names propagate:**

The current flow is: `processRuleAnnotation()` -> `applyRule()` -> returns `String` (error message or null). Rule names are available from `RuleDefinition.parse()` but discarded after lookup.

New flow introduces a result record to carry both pieces:

```java
// New internal record (package-private, not part of public API)
record RuleResult(String ruleName, String errorMessage) {}
```

Changes:
1. `applyRule()` returns `RuleResult` instead of `String` (or null if validation passes)
2. `processRuleAnnotation()` collects `List<RuleResult>` and splits into parallel `messages` and `rules` lists
3. `validateAnnotatedElement()` builds `ValidationError` with both lists
4. `validateValue()` similarly collects `RuleResult` pairs and builds the enriched `ValidationError`

**Custom message behavior:** When `@Rule(value="required|min:3", message="Field is invalid")` has a custom message and multiple rules fail, the custom message is used once (not duplicated per failed rule). The `rules` list contains all failed rule names, and `messages` contains the single custom message. In this case the parallel invariant relaxes — `rules` may be longer than `messages`. Consumers should not assume equal length; iterate `messages` for display, use `rules` for programmatic checks.

**Nested validation (`collectNestedErrors`):** Nested `ValidationError` objects already carry `rules`. When flattening into parent error strings (e.g., `"address.city: must be at least 3 characters"`), the rule names from nested errors are preserved and propagated up.

**`ValidationAspect` custom message path:** `ValidationAspect.validateMethodParameters()` has its own custom message handling — it calls `Validator.validateValue()` then replaces the error with a new `ValidationError(paramName, List.of(rule.message()))`. After the enrichment change, this branch must preserve the `rules` list from the original `ValidationResponse` when constructing the replacement `ValidationError`, so that rule metadata is not lost.

**Impact:** Every `ValidationError` construction site must be updated — `Validator` core, all tests, Spring `GlobalExceptionHandler`, and `ValidationAspect`'s custom message branch. The Spring error response JSON will include the `rules` field. This is a binary-incompatible change, acceptable before 1.0.

**Example response:**

```json
{
  "valid": false,
  "errors": [
    {
      "field": "username",
      "messages": ["Username is required", "Username too short"],
      "rules": ["required", "min"]
    },
    {
      "field": "email",
      "messages": ["The email field must be a valid email address"],
      "rules": ["email"]
    }
  ]
}
```

### 2.2 Min/Max Collection Support

**Problem:** `MinRule` and `MaxRule` only handle strings. Laravel's `min`/`max` also work on collections.

**Change:** Extend both rules to handle:
- `String` -> character length (existing)
- `Collection` -> item count (new)
- `Array` -> length (new)
- `Number` -> returns a helpful error message: "Use 'gte'/'lte' for numeric minimum/maximum validation" (explicit rather than silently passing)

**Error messages adapt to type:**
- String: "must be at least {n} characters"
- Collection/Array: "must have at least {n} items"

## 3. New Rules

### 3.1 `not_in` Rule

Inverse of `in`. Rejects values matching any in the comma-separated list.

- **Syntax:** `@Rule("not_in:admin,root,superuser")`
- **Null handling:** null passes (let `required` handle it)
- **Error message:** "The {field} field must not be one of: {values}."
- **Note:** `NotInRule` must override `getName()` to return `"not_in"` (default derivation from class name produces `"notin"`). Follows pattern established by `NullableRule`.

### 3.2 `starts_with` / `ends_with` Rules

String prefix/suffix validation with multiple allowed values.

- **Syntax:** `@Rule("starts_with:https,http")`, `@Rule("ends_with:.com,.org")`
- **Behavior:** Passes if the string starts/ends with any of the comma-separated values
- **Null handling:** null passes
- **Error messages:**
  - "The {field} field must start with one of: {values}."
  - "The {field} field must end with one of: {values}."
- **Note:** `StartsWithRule` and `EndsWithRule` must override `getName()` to return `"starts_with"` and `"ends_with"` respectively (default derivation produces `"startswith"` / `"endswith"`).

### 3.3 `bail` Rule

Flow control flag — stops validating a field after the first rule failure.

- **Syntax:** `@Rule("bail|required|min:3|email")`
- **Error message:** None (never fails).

**Detection mechanism:** `BailRule` implements a marker interface `FlowControlRule` (new interface, extends `ValidationRule`). In the validation loop (`processRuleAnnotation` and `validateValue`), after resolving a rule from the registry, check `rule instanceof FlowControlRule`. If true, set a `bailOnFailure` flag for the current field. On subsequent rule failures, break out of the loop immediately.

This approach avoids brittle string comparisons against rule names and establishes a clean pattern for any future flow-control rules. `BailRule.validate()` always returns null.

**`validateValue()` support:** Yes — `bail` works in `validateValue()` using the same `FlowControlRule` check in its iteration loop.

### 3.4 `ip` Rule Update — IPv4/IPv6 Support via Parameter

Single `IpRule` class handling all three variants via parameter:

- `@Rule("ip")` -> validates either IPv4 or IPv6
- `@Rule("ip:v4")` -> IPv4 only (current behavior)
- `@Rule("ip:v6")` -> IPv6 only

IPv6 validation covers: standard 8-group hex, `::` shorthand, and mixed IPv4-mapped notation.

### 3.5 Rule Registration

All new rules (`not_in`, `starts_with`, `ends_with`, `bail`) must be registered in `BuiltInRules.registerAll()`. The `ip` rule already exists and is updated in place; `ipv4` and `ipv6` are not separate registrations since `ip` handles them via parameter.

## 4. Code Quality Fixes

### 4.1 EmailRule Regex Tightening

**Problem:** Current regex accepts `.@example.com` and `test..email@example.com`.

**Fix:** Stricter pattern that disallows:
- Leading/trailing dots in local part
- Consecutive dots in local part
- Leading/trailing hyphens in domain

**Note:** This is a potentially breaking change for users whose data contains technically-invalid-but-previously-accepted addresses. Acceptable for a pre-1.0 release.

## 5. Test Coverage

### 5.1 EnumRule Dedicated Test Class

New `EnumRulesTest` covering:
- Valid enum values pass
- Invalid enum values fail
- Null handling (passes)
- Custom error messages
- Missing `enumClass` parameter error

### 5.2 Invalid Rule Parameter Tests

Test graceful handling of misconfigured rules:
- `between:100,50` (max < min)
- `min:abc` (non-numeric parameter)
- `regex:invalid[` (malformed regex)
- Empty field reference in conditional rules: `required_if:,value`

Behavior depends on strict mode — strict throws `IllegalArgumentException`, non-strict converts to validation error.

### 5.3 Concurrency Tests

- Multiple threads calling `Validator.validate()` simultaneously
- Concurrent rule registration via `RuleRegistry`
- `Validator.setConfig()` during concurrent validation

### 5.4 Tests for All New/Changed Code

Every bug fix and new feature gets corresponding tests:
- InRule null handling
- Numeric comparison with large values, decimals, and Long range
- Spring GlobalExceptionHandler merging duplicate field errors
- ValidationError `rules` field populated correctly (with and without custom messages)
- Min/Max on collections, arrays, and helpful error for Number types
- All new rules (`not_in`, `starts_with`, `ends_with`, `bail`, `ip` / `ip:v4` / `ip:v6`)
- Tightened EmailRule rejections (leading dot, consecutive dots, trailing dot)
- `bail` stops validation after first failure
- `FlowControlRule` marker interface detection

## Decisions Log

| Decision | Choice | Rationale |
|----------|--------|-----------|
| ValidationError enrichment | Separate `rules` field, always populated | Enables programmatic error handling, i18n, while keeping messages human-readable |
| Custom message + rules list | `rules` lists all failed rules; `messages` contains single custom message (not duplicated) | Clean UX — custom message is the user's intent, rule names are metadata |
| Internal result type | `RuleResult` record (package-private) | Carries rule name + message through the validation pipeline without changing public API |
| Bail detection | `FlowControlRule` marker interface | Clean extensibility pattern, avoids string comparison |
| Min/Max scope | Strings + collections, not numbers | No overlap with `gte`/`lte`, clear separation of concerns |
| Min/Max on Number | Helpful error message, not silent pass | Prevents user confusion |
| Bail syntax | In pipe chain (`bail\|required\|min:3`) | Matches Laravel syntax, users expect it there |
| Type-checking rules | Skipped | Java's type system handles this at compile time |
| EmailRule | Tighten regex, not full RFC 5322 | Matches practical validation needs without over-engineering |
| IP rule structure | Single class with parameter (`ip`, `ip:v4`, `ip:v6`) | Less code, follows existing parameter pattern |
| DateRule format fix | Removed — bug does not exist | Code already handles date types correctly when format parameter is present; verified by reading `DateRule.java` |
| Numeric parameter parsing | Change to `Double.parseDouble()` | Supports decimal thresholds and matches `doubleValue()` conversion |
