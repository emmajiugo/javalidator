# Javalidator Pre-1.0.0 Improvements Design

**Date:** 2026-03-21
**Status:** Approved
**Scope:** Bug fixes, API changes, new rules, code quality, and test coverage before tagging 1.0.0

---

## 1. Bug Fixes

### 1.1 InRule Null Handling

**Problem:** `InRule.validate()` calls `String.valueOf(value)` without a null check, converting null to the string `"null"`. All other rules return null (pass) for null values.

**Fix:** Add null guard at the top of `InRule.validate()`. Return `null` for null values — let `required` handle null enforcement.

### 1.2 Numeric Comparison Precision

**Problem:** `GtRule`, `LtRule`, `GteRule`, `LteRule` cast to `int` via `intValue()`, causing silent overflow for values > 2,147,483,647 and truncating decimals. `BetweenRule` already uses `doubleValue()` correctly.

**Fix:** Change all four rules to use `doubleValue()` instead of `intValue()`.

### 1.3 Spring Metadata Defaults Mismatch

**Problem:** `additional-spring-configuration-metadata.json` says `validate-get-requests` and `validate-delete-requests` default to `false`, but `JavalidatorProperties.java` initializes them to `true`.

**Fix:** Update the metadata JSON to set both defaults to `true`.

### 1.4 Multi-@Rule Error Aggregation in Spring Aspect

**Problem:** `ValidationAspect.validateMethodParameters()` replaces errors when a parameter has multiple `@Rule` annotations with custom messages. Only the last failing rule's error is reported.

**Fix:** Accumulate errors across all `@Rule` annotations on the same parameter instead of replacing.

## 2. API Changes

### 2.1 ValidationError Enrichment

**Problem:** `ValidationError(String field, List<String> messages)` provides no programmatic way to identify which rules failed. This blocks i18n, conditional UI logic, and error handling.

**Change:** Extend the record to:

```java
record ValidationError(String field, List<String> messages, List<String> rules)
```

- `rules` is always populated with failed rule names (e.g., `["required", "min"]`)
- `messages` remains human-readable (custom or default)
- Lists are parallel: `rules.get(i)` corresponds to `messages.get(i)`

**Impact:** Every `ValidationError` construction site must be updated — `Validator` core, all tests, Spring `GlobalExceptionHandler`. The Spring error response JSON will include the `rules` field.

**Example response:**

```json
{
  "valid": false,
  "errors": [
    {
      "field": "username",
      "messages": ["Username is required", "Username too short"],
      "rules": ["required", "min"]
    },
    {
      "field": "email",
      "messages": ["The email field must be a valid email address"],
      "rules": ["email"]
    }
  ]
}
```

### 2.2 Min/Max Collection Support

**Problem:** `MinRule` and `MaxRule` only handle strings. Laravel's `min`/`max` also work on collections.

**Change:** Extend both rules to handle:
- `String` -> character length (existing)
- `Collection` -> item count (new)
- `Array` -> length (new)
- `Number` -> unchanged (use `gte`/`lte` for numeric comparison)

**Error messages adapt to type:**
- String: "must be at least {n} characters"
- Collection/Array: "must have at least {n} items"

## 3. New Rules

### 3.1 `not_in` Rule

Inverse of `in`. Rejects values matching any in the comma-separated list.

- **Syntax:** `@Rule("not_in:admin,root,superuser")`
- **Null handling:** null passes (let `required` handle it)
- **Error message:** "The {field} field must not be one of: {values}."

### 3.2 `starts_with` / `ends_with` Rules

String prefix/suffix validation with multiple allowed values.

- **Syntax:** `@Rule("starts_with:https,http")`, `@Rule("ends_with:.com,.org")`
- **Behavior:** Passes if the string starts/ends with any of the comma-separated values
- **Null handling:** null passes
- **Error messages:**
  - "The {field} field must start with one of: {values}."
  - "The {field} field must end with one of: {values}."

### 3.3 `bail` Rule

Flow control flag — stops validating a field after the first rule failure.

- **Syntax:** `@Rule("bail|required|min:3|email")`
- **Implementation:** `BailRule.validate()` always returns null. The `Validator` checks if `bail` was encountered when iterating rules and breaks on first failure for that field.
- **Error message:** None (never fails).

### 3.4 `ip` Rule Update — IPv4/IPv6 Support via Parameter

Single `IpRule` class handling all three variants via parameter:

- `@Rule("ip")` -> validates either IPv4 or IPv6
- `@Rule("ip:v4")` -> IPv4 only (current behavior)
- `@Rule("ip:v6")` -> IPv6 only

IPv6 validation covers: standard 8-group hex, `::` shorthand, and mixed IPv4-mapped notation.

## 4. Code Quality Fixes

### 4.1 EmailRule Regex Tightening

**Problem:** Current regex accepts `.@example.com` and `test..email@example.com`.

**Fix:** Stricter pattern that disallows:
- Leading/trailing dots in local part
- Consecutive dots in local part
- Leading/trailing hyphens in domain

### 4.2 DateRule Format Parameter Fix

**Problem:** `@Rule("date:yyyy-MM-dd")` on a `LocalDate` field fails because the rule only tries to parse strings when a format parameter is present.

**Fix:** If the value is already a date type (`LocalDate`, `LocalDateTime`, `Date`), it's valid regardless of the format parameter. The format only applies to string parsing.

## 5. Test Coverage

### 5.1 EnumRule Dedicated Test Class

New `EnumRulesTest` covering:
- Valid enum values pass
- Invalid enum values fail
- Null handling (passes)
- Custom error messages
- Missing `enumClass` parameter error

### 5.2 Invalid Rule Parameter Tests

Test graceful handling of misconfigured rules:
- `between:100,50` (max < min)
- `min:abc` (non-numeric parameter)
- `regex:invalid[` (malformed regex)
- Empty field reference in conditional rules: `required_if:,value`

Behavior depends on strict mode — strict throws `IllegalArgumentException`, non-strict converts to validation error.

### 5.3 Concurrency Tests

- Multiple threads calling `Validator.validate()` simultaneously
- Concurrent rule registration via `RuleRegistry`
- `Validator.setConfig()` during concurrent validation

### 5.4 Tests for All New/Changed Code

Every bug fix and new feature gets corresponding tests:
- InRule null handling
- Numeric comparison with large values and decimals
- Multi-@Rule error aggregation in Spring aspect
- ValidationError `rules` field populated correctly
- Min/Max on collections and arrays
- All new rules (`not_in`, `starts_with`, `ends_with`, `bail`, `ip` variants)
- Tightened EmailRule rejections
- DateRule with date types + format parameter

## Decisions Log

| Decision | Choice | Rationale |
|----------|--------|-----------|
| ValidationError enrichment | Separate `rules` field, always populated | Enables programmatic error handling, i18n, while keeping messages human-readable |
| Min/Max scope | Strings + collections, not numbers | No overlap with `gte`/`lte`, clear separation of concerns |
| Bail syntax | In pipe chain (`bail\|required\|min:3`) | Matches Laravel syntax, users expect it there |
| Type-checking rules | Skipped | Java's type system handles this at compile time |
| EmailRule | Tighten regex, not full RFC 5322 | Matches practical validation needs without over-engineering |
| IP rule structure | Single class with parameter (`ip`, `ip:v4`, `ip:v6`) | Less code, follows existing parameter pattern |
